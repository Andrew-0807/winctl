# WinCTL (Tauri) Audit — 2026-07-06

Scope: `src-tauri/` Rust backend + repo hygiene. Read, not guessed.
The old `SLOP-AUDIT.md` is ~80% addressed (restart re-execs, exec-kill stores children,
uptime uses LastBootUpTime, memory field renamed, sysinfo deduped, fetch drops lock,
display-off uses correct SendMessage, WS forwards typed messages). Below is what's **still
open** plus **new** findings.

Severity: **[BROKEN]** wrong behavior · **[SEC]** security · **[SLOP]** careless · **[BOMB]** future pain.

---

## 1. Auto-restart is dead for services WinCTL itself started [BROKEN] — headline feature

`process.rs:271-296` `is_process_alive`. For a self-spawned service it returns
`proc.child.as_ref().and_then(|c| c.id()).is_some()`.

`tokio::process::Child::id()` returns `Some` until the child is **reaped** (`wait`/`try_wait`).
The only `wait()` in the codebase is inside `kill()` (`process.rs:191`). Nothing ever polls a
*running* child to completion. So after a managed process crashes, `id()` still returns the old
PID → `is_process_alive` reports `true` forever → the supervision loop (`lib.rs:1358`) never
restarts it, and the UI shows it "running" while it's dead.

Only **externally-owned** processes get real liveness (they query `GetExitCodeProcess`).
So the README's "Auto-restart crashed services" only works for processes WinCTL *didn't* spawn.

**Fix:** for self-spawned, call `child.try_wait()` and treat `Ok(Some(_))` as dead; or query
`GetExitCodeProcess` on the stored PID like the external path already does.

## 2. exec allowlist is bypassable with one shell metacharacter [SEC]

`lib.rs:752-759` + `777`. Allowlist checks only the **first whitespace token's basename**, then
runs the **entire** `req.command` through `cmd.exe /C`. So with `echo` allowlisted:

```
echo hi & whoami        # basename "echo" passes, runs both
echo hi && del *.*      # runs the second command too
```

Every `cmd.exe` metacharacter (`&`, `&&`, `|`, `>`, `for`) escapes the allowlist.
Mitigated by: exec disabled by default + behind auth. Still, the allowlist gives false safety.

**Fix:** parse args yourself and spawn the exe directly (no `cmd.exe`), or reject any command
containing shell metacharacters.

## 3. Pre-onboarding setup can be hijacked cross-origin [SEC]

`lib.rs:1120-1131`. `/api/setup/complete` (and `/register`) live on `public_routes`, which has
**no** `auth_layer` — the loopback/Origin CSRF check only guards `protected_routes`. CORS is
`AllowOrigin::any()`. On a fresh install, before the user finishes onboarding, any website they
visit can `POST http://localhost:8888/api/setup/complete` and set its own password +
`open_access:true`. The idempotency guard (`onboarding_complete`) only closes the window *after*
legit setup, not before.

**Fix:** apply the same loopback-only / Origin check to the setup routes, or require a one-time
setup nonce shown in the app window.

## 4. `/api/fonts` still unauthenticated + blocking PowerShell [BOMB]

`lib.rs:1124` — on `public_routes`. `get_fonts` (`lib.rs:862`) cold-starts PowerShell +
`InstalledFontCollection` synchronously (~1-3s, blocks a worker thread). Any anonymous caller can
loop it to starve the pool. This was item #12 in the old audit; never moved behind auth or cached.

**Fix:** move behind auth, cache the result once, or read
`HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Fonts`.

---

## 5. `get_system_info` shells out to PowerShell on every call [SLOP]

`lib.rs:697-705`. Uptime spawns PowerShell + `Get-CimInstance Win32_OperatingSystem` per
`/api/system` hit (~200-500ms cold start, blocking). The dashboard polls this.

**Fix (one line):** `GetTickCount64() / 1000` via `windows`/`winapi`. No process spawn.

## 6. CLI `start`/`stop`/`restart` can't manage the daemon — contradicts README [BROKEN]

`lib.rs:1600-1604` routes top-level `start|stop|restart` to `run_cli`, which
(`lib.rs:1805-1837`) POSTs to `/api/services/{id}/{action}` with an **empty** id and needs the
daemon **already running**. But README documents `winctl start` = *start the daemon* and
`winctl stop` = *stop it*. Effects:
- `winctl start` on a stopped machine → "server is not running." No CLI path launches the daemon
  at all (you must run the bare exe / `--headless`).
- `start` and `start-svc` are identical (both map to `"start"`), so the svc aliases are redundant.
- `winctl stop` (no id) hits `/api/services//stop` → 404, never stops the daemon.

**Fix:** make bare `start/stop/restart` target the daemon (spawn exe / POST `/api/shutdown`),
and keep `*-svc` for services. Or fix the README. Right now code and docs disagree.

## 7. Two sources of truth for config [BOMB]

`AppState` holds `services`/`settings` in `Arc<RwLock>`, and `config.rs` keeps a separate global
5s-TTL cache (`SERVICES_CACHE`/`SETTINGS_CACHE`). Handlers mutate the RwLock and write-through, so
they stay aligned *today*, but anything reading via `config::read_settings()` after startup
(`copy_password_to_clipboard`, `--pass`) can serve stale data for up to 5s. Two caches for one
value is a latent divergence waiting for the next feature.

**Fix:** drop the file-level cache; the RwLock is already the live copy. YAGNI on the TTL.
